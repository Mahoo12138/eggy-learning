# 蛋仔商城道具配送中心完整课程大纲

## 课程定位与最终作品

巅峰凤凰蛋继续以“蛋仔商城道具配送中心”为唯一累积作品，保留订单、库存、工作线程、任务队列、竞态、双仓转移与安全关店的原方向。重构后的主线是：先用 C++ 封装保护业务不变量，再完成真实 CPU 密集计算与等价优化，最后用并发处理把同一套代码组合成可运行的配送中心。

课程使用 C++20。前两章讲清对象与所有权，中间五章建立计算和调度，后三章完善一致性与生命周期。不要求学习者根据一句“实现线程池”自行猜出整套基础设施，也不加入与本作品无关的继承树、元编程或第三方框架。

最终作品包括真实的订单对象、可重复路线评分、AoS/SoA 等价实现、独立输出槽位的并行计算、有界阻塞队列、固定线程池、future 结果通道、库存幂等与冲突处理、双仓转移、协作取消和完整配送中心。双仓模块与配送库存是同工程中的两项业务演示，不声称二者已接入同一跨模块库存事务。

## 计算模型与性能边界

路线评分是用来学习密集计算、数据布局和调度的**可重复整数模型**，不是实际地图导航算法。每条候选路线有若干路段，每段带 `x/y/toll`；`segmentCost` 对订单种子和路段字段做 24 轮整数混合，候选总代价是路段代价之和。基准按候选索引升序遍历，严格更小时更新，平局保留最小索引。

混合函数使用 `uint64_t` 的定义明确回绕；业务代价则由范围约束避免溢出：单段最多 65535，路段上限 4096，所以一条路线代价最多 268431360。不能把这个教学模型的无符号回绕推广到真实金额、库存或有符号整数运算。

`RouteWorkload` 的 AoS 已经是连续 `vector<RouteSample>`。`PackedRoutes` 把字段拆成三个连续数组，属于 SoA。因为评分同时需要三个字段且计算较重，SoA 未必比 AoS 快，多线程也不保证在小输入下更快。基准应说明布局准备成本，消费真实计算结果，完成逐项等价检查，再记录多轮串行、优化与并行耗时。不得用 sleep、硬编码耗时、漂亮的一次结果或固定加速倍数作为验收目标。

队列要求元素可 noexcept 移动，本课程演示使用 int 和已交付的任务包装；不直接把有潜在抛异常复制的 Order 换成队列元素。线程池只接受外部提交者，拒绝 worker 向同池嵌套 submit/shutdown；所有者需保证调用者结束后再销毁对象，不能从自身工作线程析构线程池。

Cancel 只丢弃尚未开始的排队任务，其 future 抛出 broken_promise；已经开始的任务正常完成。`scoreCancellable` 另用 stop_token 在候选边界检查取消并返回 nullopt，它没有自动接入 DeliveryCenter 的 Cancel。两种合同不能混为“立即强杀正在执行的线程”。

## 第 1 章：把订单规则封装在对象内部

**目标：**通过 Order(id, units, routeSeed) 的构造校验、private 字段、const 读取与值语义，保护合法订单状态。

**阶段：**封装与对象边界。**章末完整状态：**`cpp-domain-model-3`。

### 概念小节：为什么一笔订单不应允许任意改成负数

如果订单字段完全开放，调用者能把数量写成 -3，或把编号清空；后续算法即使能够编译，业务输入也已失效。现在 Order 把这些字段收为 private，构造入口统一校验，调用者通过 const 读取函数使用合法对象。

封装不是把每个字段加一对 getter/setter，而是把状态与允许的操作放在同一个边界里。构造入口验证不可缺少的条件，public 表达业务操作，private 保存实现细节；const 读取承诺不改变这个对象的可观察状态。值语义让每份订单有清楚的生命期和复制行为。

- **封装与不变量：**不变量是对象在公开操作前后都必须成立的条件；封装让检查规则只有一个可信入口。 对应代码：阅读 src/domain.hpp 中 Order(id, units, routeSeed) 的 private 字段和构造校验，列出类外禁止的写入。
- **public 与 private：**public 是调用者能用的接口，private 是类自己维护的内部状态；访问限制发生在编译期。 对应代码：尝试在练习副本中直接修改私有字段，观察编译器拒绝，再恢复文件。
- **const 与只读引用：**const T& 借用对象并限制通过这个引用修改对象，避免不必要的复制；它不自动保证其他线程不能修改同一对象。 对应代码：查看 getter 的 const 修饰和接收订单的 const 引用参数。
- **值语义：**复制一个值后得到独立对象；修改副本不应意外改变原对象。移动则转移资源，不是两份共享所有权。 对应代码：在 tests/tests.cpp 比较复制前后的订单字段和独立生存期。

**完整推演：合法订单跨过边界后如何被使用**

1. 构造数量为 2 的 Order，读取接口返回已校验的编号、数量和路线种子。
2. 尝试构造数量为 0 或编号为空的 Order，构造阶段报告错误，不留下半合法对象。
3. 通过 const Order& 读取订单，避免为只读使用复制整笔对象。
4. 把有效订单复制到待计算列表，原订单与副本各自拥有数据；后续生命周期清楚。

先让非法状态难以进入，再让后续模块依赖这个合同。

- 订单数量只能大于 0，最可靠的约束放在哪里？
- 计算函数读取数量时，哪种接口最能维护对象边界？
- 函数接收 const Order& 最直接表达什么？

## 第 2 章：用对象生命期管理资源

**目标：**理解 RAII、独占所有权、移动语义与异常展开，让正常返回和异常路径遵守同一清理规则。

**阶段：**封装与对象边界。**章末完整状态：**`raii-ownership-3`。

### 概念小节：抛出异常后谁负责清理资源

手动申请资源后，正常路径会释放，但中间的 return 或 throw 容易绕过释放。把资源交给有析构行为的对象后，离开作用域会统一触发回收。

RAII 把“获得资源”和“建立拥有者”绑定，把“离开作用域”和“释放资源”绑定。局部对象按构造的逆序析构，异常展开也遵守这一规则。独占资源不能被随意复制，移动可以把唯一拥有权交给新对象；借用者不负责释放。

- **RAII：**Resource Acquisition Is Initialization：资源在对象初始化时获得，在对象析构时释放。资源包括内存、锁、文件和线程生命期。 对应代码：ownership.hpp 中 RouteTable 拥有 vector 数据，DispatchSession 用 unique_ptr<RouteTable> 独占表并拥有 vector<Order>。
- **独占所有权：**同一份资源在同一时刻只有一个负责释放的对象，其他引用只是借用。 对应代码：DispatchSession 禁止复制，移动后原会话不能再读取已转走的 RouteTable；访问时报告错误。
- **移动语义：**std::move 只是把表达式转换为可供移动的类别，是否真正转移资源取决于类型的构造或赋值操作。独占拥有者移动后不再拥有原资源，但仍能安全析构。 对应代码：对照 Order 显式复制操作与 DispatchSession 移动操作：std::move(order) 仍调用复制，原订单有效；移动 DispatchSession 则转走 unique_ptr 和 vector。
- **异常安全：**操作失败后仍维护对象不变量并释放已获得资源；它不意味着所有失败都能自动回滚。 对应代码：在 DispatchSession 创建后抛出异常，验证拥有对象随栈展开清理；RAII 不等于自动回滚业务记录。

**完整推演：一个资源跨过移动与异常边界**

1. 创建拥有者 A，此时资源有且只有一个负责释放者。
2. 把 DispatchSession A 移动给 B，A.routes() 被明确拒绝，B 接手 RouteTable 和订单列表。
3. 在 B 所在作用域抛出一个受测试捕获的异常。
4. 栈展开先析构 B，释放资源；随后析构空的 A，不发生二次释放。

清理责任跟着拥有权走，不跟着变量名称或正常执行路径走。

**理解检查：**

- 资源建立后立即 throw，什么保证已建立的局部拥有者被清理？
- 把独占拥有者 A 移动到 B 后，谁负责原资源？
- 返回指向局部拥有者内部数据的引用后局部对象被析构，会怎样？

## 第 5 章：让多个工作人员并行算路线

**目标：**把独立订单划分给真实线程，使用不重叠输出和结束同步，保持与串行基准一致。

**阶段：**并行与调度。**章末完整状态：**`worker-threads-3`。

### 概念小节：几个线程真的能同时算，却不能同时乱改一个容器

多个工作线程完成订单的先后顺序由调度决定。若它们一起 push_back 到同一个 vector，即使处理的是不同订单也可能争用容器内部状态。预先分配结果，再让每个索引只有一个写入者，可以消除这类冲突。

订单输入在全部工作线程结束前保持有效且只读，输出提前分配。parallelFor 用 atomic<size_t>::fetch_add 为每次领取返回唯一旧值，所以每个合法索引只交给一个线程；不是预先分配固定连续区间。std::jthread 在离开作用域时完成回收，之后主线程才读结果或重新抛出捕获的异常。

- **并发与并行：**并发是多个任务的生命期交叠，并行是多个任务在不同执行资源上同时计算；线程存在不等于总能获得多个核心。 对应代码：workers.hpp 使用 std::jthread 建立真实线程；可用核心与调度决定是否真正同时运算。
- **不重叠写入：**多个线程可分别写普通容器中不同的已有元素，前提是不同时改变容器结构且每个元素只有一个写入者。 对应代码：parallelScores 预先分配输出，再通过索引写入；不在 worker 中共享 push_back。
- **join 与生命期：**join 等待目标线程完成，同时使已完成线程的效果可以在同步后的主线程中读取；被借用数据必须活到工作结束。 对应代码：parallelFor 的 jthread 容器退出作用域时逐一 join，完成后才读 first_error 并重新抛出。
- **线程异常汇合：**工作线程中的未捕获异常不会自动从 main 的 try/catch 出现，必须在工作边界捕获并通过明确通道返回。 对应代码：保存 exception_ptr，在完成 join 后由调用线程重新抛出。
- **原子领取索引：**fetch_add 把读取旧值和递增作为一个不可分割操作，因此竞争领取者获得不同索引。这里的 relaxed 用于唯一分配，不承担结果发布，结果可见性由结束同步建立。 对应代码：next.fetch_add(1, memory_order_relaxed) 分配槽位；不要用普通 size_t++ 替代并发领取。

**完整推演：五笔订单分给两个线程**

1. 准备 5 个结果槽位，索引是 0 到 4。
2. 线程 A、B 通过 next.fetch_add(1) 逐个领取唯一索引，例如 A 得 0、B 得 1、B 又得 2；分工取决于调度，但不会重复领取。
3. 即使 B 先结束，它也只写属于自己的槽位，不移动其他结果。
4. 主线程等待 A、B 完成，再按索引与串行基准逐项比较。
5. 若 A 某次评分抛出异常，先回收所有已启动线程，再让调用者看到失败。

共享只读数据与独占输出位置把同步需求缩小到生命期和汇合边界。

- 每个线程计算一笔不同订单，哪种输出方式最清楚地避免容器结构竞争？

## 第 6 章：订单多了怎样等待而不空转

**目标：**用有界阻塞队列建立生产消费合同，掌握互斥量、谓词等待、背压和关闭唤醒。

**阶段：**并行与调度。**章末完整状态：**`blocking-queue-3`。

### 概念小节：通知不是订单，唤醒后还要重新看条件

消费者若一直 while 检查空队列会浪费 CPU；生产者若无限积压则占满内存。条件变量让线程睡到条件可能变化，但醒来时队列可能仍为空，或已被另一消费者取走。

互斥量保护队列内容和关闭状态。消费者等待“有数据或已关闭”，生产者等待“有空间或已关闭”；wait 临时释放锁，醒来重新取得锁并检查谓词。容量把积压限制住，形成背压。关闭是状态转换，必须唤醒等待的两类线程，并明确排空或取消。

- **互斥量与临界区：**mutex 让同一时刻只有一个线程操作受保护共享状态；检查与修改必须处于一致边界。 对应代码：queue.hpp 的队列、容量和关闭标志使用同一互斥协议。
- **条件变量与谓词等待：**条件变量只是等待通知的机制；谓词表达真正可继续的状态，wait 醒来后必须重检。 对应代码：pop 等待非空或关闭，push 等待未满或关闭，使用 wait(lock,predicate)。
- **有界队列与背压：**容量限制积压量；队列满时生产者等待或得到明确拒绝，防止任务无限吞噬内存。 对应代码：BoundedQueue<T>(capacity) 拒绝零容量，push(T) 等到有空间或返回关闭结果。 本示例队列要求元素可 noexcept 移动，使用 int 或线程池提供的任务包装；不要直接换成可能抛异常复制的 Order。
- **关闭协议：**关闭要同时定义是否接收新任务、如何处理已有元素，以及等待者如何退出。 对应代码：close(Drain) 排空已入队任务，close(Cancel) 清掉待领取元素，pop 结束返回 nullopt。

**完整推演：容量为 1 的队列在关闭时发生什么**

1. 生产者先把任务 A 放入队列，队列已满。
2. 生产者想提交 B，发现没有空间，进入条件变量等待并释放锁。
3. 控制线程执行 Drain 关闭，改变关闭状态并通知生产者与消费者。
4. 生产者醒来发现已关闭，B 提交失败，不再等待空间。
5. 消费者仍可取出 A；再次 pop 时看到关闭且为空，返回结束。

关闭通知必须覆盖两种等待者；排空保留已接收任务，拒绝尚未入队任务。

- Drain 关闭后，pop 应在何时返回结束？

## 第 7 章：把线程、队列和结果封装成线程池

**目标：**让固定工作线程持续接收任务，用 future 返回值或异常，避免把线程细节泄漏给业务调用者。

**阶段：**并行与调度。**章末完整状态：**`task-pool-3`。

### 概念小节：提交一次计算，应该拿到结果而不是接管一条线程

一次性线程会反复启动和回收。固定线程池把工作线程保留，让任务通过有界队列进入；调用者得到 future，用它领取值或异常，不需要知道是哪条线程执行。

线程池封装三件事：固定数量工作线程、接收任务的有界队列、每个任务的结果通道。任务从提交者移入队列，再由某个 worker 独占执行。packaged_task 把返回值或异常写入共享结果状态，future.get 读取它。关闭后不再接受提交；排空执行已接收任务，取消销毁排队任务，等待者得到可识别的取消结果。

- **线程池与封装：**线程池把线程创建、工作循环、排队和关闭协议收在一个对象中，业务只提交任务并领取结果。 对应代码：TaskPool(workers,capacity) 拥有 worker 和 BoundedQueue，业务不手动 join 单个任务线程。
- **packaged_task 与 future：**packaged_task 保存一次可执行任务及结果状态；future 是调用者持有的一次性结果读取端。 对应代码：submit(callable) 返回 future；get 返回计算值或抛出任务内的异常。
- **有界提交与嵌套调用：**有界队列可能阻塞提交者；如果全部 worker 都在向同池提交并等待，可能没有线程继续消费。 对应代码：本工程明确拒绝从同一池的工作线程进行嵌套 submit 或 shutdown，保留简单可验证的合同。
- **异常传播与取消结果：**任务异常是该任务的结果，不能悄悄吞掉；尚未执行的 packaged_task 被销毁后，future 会看到 broken_promise。 对应代码：Cancel 清除排队任务，已运行任务仍执行到结束；调用者用 future_error 区分未执行任务。

**完整推演：三个任务中一个失败，线程池是否还活着**

1. 提交任务 A、B、C，各得到独立 future。
2. A 返回路线结果，future A.get 正常返回。
3. B 抛出异常，packaged_task 保存异常；worker 不因这个业务异常退出。
4. C 仍能执行并返回，future B.get 在调用线程重新抛出原异常。
5. 关闭时选择 Drain，已接收任务全部结束，再回收所有固定线程。

异常隔离发生在任务结果边界，不能用一个默认值冒充失败任务。

- 任务函数抛出业务异常后，调用者从哪里看到它？

## 第 8 章：让库存与订单记录一起成立

**目标：**把库存检查、扣减、幂等记录封装为一个原子业务动作，区分重试与冲突。

**阶段：**一致性与生命周期。**章末完整状态：**`inventory-race-3`。

### 概念小节：只有一个库存，为什么两笔订单都说自己成功

线程 A 读到 1，线程 B 也读到 1；两者都通过检查后各自发货。即使每次读写单独上锁，整个业务动作仍可能被拆开。同一订单重试还可能再次扣减。

库存类隐藏数量与订单处理记录，公开 checkout(Order) 表达一次业务动作。先在锁外做耗时计算，再进入一个短临界区：查订单是否处理过、核对内容、检查库存、扣减并记录结果。同号同内容返回原结果，不再次扣减；同号不同内容明确冲突。结果是本进程内记忆，不是跨重启的持久化账本。 如果同一编号的不同内容同时竞争，以先获得库存锁并写下记录的一方为准，不承诺先提交线程池者先处理。Receipt.remaining 是首次结果的历史库存快照，当前值通过 stock() 读取。

- **数据竞争与业务竞态：**数据竞争涉及未同步的共享内存访问；业务竞态还包括每次访问都同步、但多个步骤合起来不原子的情况。 对应代码：仅分别保护读取与写回不够；检查 checkout 的完整锁范围。
- **原子临界区：**业务上不可分割的一组动作由同一锁保护，使其他线程看不到中间状态。 对应代码：inventory.hpp 将结果查询、内容比较、库存检查、扣减和记录放进统一操作。
- **幂等性与冲突：**相同标识和相同内容重试应返回已确定结果；相同标识却更改内容必须拒绝，不能混成新订单。 对应代码：Receipt 的 duplicate 标志与 Conflict 状态区分重试和冲突；比较 units 与 routeSeed。 并发冲突测试只要求一个指纹成为既定结果，不要求固定线程获胜。
- **一致性边界：**内存锁只协调当前进程里的线程；进程退出后，未持久化的订单记录不会自动保留。 结果表在本例中不自动淘汰，长期运行还要设计容量与持久化策略。 对应代码：Inventory 的内存记录覆盖本次运行，课程不把它冒充跨重启的数据库事务。

**完整推演：先成功、再重试、再冲突**

1. 初始库存为 3，订单 A 请求 2 件，进入 checkout 后成功并记录结果，库存变为 1。
2. 另一个线程重交相同 A、2 件、相同路线种子，命中原记录，duplicate 为真，库存仍为 1。
3. 订单编号仍是 A，但数量改为 1，内容与原记录冲突，返回 Conflict，不改库存。
4. 全新订单 B 请求 2 件，返回 Insufficient 并记录这次明确结果。
5. 后来重试同一个 B，得到它原先确定的失败结果；需要新业务尝试时使用新订单标识。

幂等不只是成功去重，还要明确重复失败与内容冲突的业务含义。

## 第 9 章：同时保护双仓库并及时响应取消

**目标：**用 scoped_lock 保证双仓转移不形成等待环，并为计算添加明确的协作取消边界。

**阶段：**一致性与生命周期。**章末完整状态：**`deadlock-cancel-3`。

### 概念小节：互斥量都用对了，为什么程序仍然永远等着

线程 A 从东仓转到西仓，先持东仓锁再等西仓锁；线程 B 反向转仓，先持西仓锁再等东仓锁。每次访问都有锁，却组成了等待环。与此同时，已经开始的长计算也不能靠清空队列立即停止。

双仓转移是跨两个对象的不变量：减少源仓、增加目的仓必须整体成立。std::scoped_lock 一次接管多把锁并在退出时释放，避免手工相反顺序锁造成的等待环。取消是另一个协议：stop_token 只表达请求，计算要在明确检查点主动观察；尚未形成完整结果时返回取消，而不是提交半份库存修改。

- **死锁与等待环：**多个线程各持有别人需要的资源并循环等待，导致没有任何一个能继续；数据没被乱写也可能发生。 对应代码：画出“线程 A 持东等西，线程 B 持西等东”的资源图，不通过真实无限挂起来证明。
- **多锁 RAII：**多锁守卫取得相关锁，离开作用域自动释放；参与同一操作的所有路径应使用一致协议。 对应代码：transfer.hpp 的 transfer 使用 std::scoped_lock 同时锁住两仓，避免自行写相反加锁顺序。
- **守恒与原子转移：**一次转仓完成后源减少量等于目的增加量，不能先暴露一边已改、另一边未改的状态。 对应代码：Warehouse 的余额由受控操作维护，测试比较转仓前后总量。
- **协作取消：**取消请求不会强杀线程；任务在自己选择的安全点检查请求并停止继续计算。 对应代码：scoreCancellable(order,PackedRoutes,stop_token) 在候选边界及返回前检查，取消时返回 nullopt。

**完整推演：反向转仓与取消如何各自收束**

1. 东仓 10、西仓 20，线程 A 要东转西 3，线程 B 要西转东 4。
2. 两条路径都用同一种双锁协议；任一线程先获得操作权，另一条等待，不形成各握一锁的环。
3. 两次转仓成功后东仓 11、西仓 19，总量仍是 30。
4. 另一任务正在评分，控制者发送 stop 请求；它在下一个已定义检查点发现取消并返回 nullopt。
5. 调用者看到 nullopt，不把尚未完成的评分当正常结果提交库存。

多锁保护业务原子性，协作取消保护生命期；两种机制解决不同问题。

## 第 10 章：汇集所有代码，完成配送与安全关店

**目标：**整合封装、串行与并行评分、线程池及库存提交，用排空与取消两种策略完成同一作品。

**阶段：**一致性与生命周期。**章末完整状态：**`graceful-shutdown-3`。

### 概念小节：关店不是把一个布尔值改成 true

停止接受订单不代表队列已空、线程已停或库存已提交。线程池任务可能仍在使用路线表和库存对象；如果先销毁这些数据再等待线程，就会出现悬空访问。

DeliveryCenter 把只读路线数据、库存和线程池组合成一个生命期明确的对象。提交任务先评分，再通过库存接口提交；shutdown 先关闭接收，按 Drain 或 Cancel 处理排队项，然后等待正在执行的任务结束。线程池先被销毁并回收 worker，之后才能释放它们引用的数据。关店完成以已接收任务结局与线程回收为证据。

- **生命周期与成员析构顺序：**成员按声明顺序构造、按相反顺序析构；后台工作必须先结束，随后才能释放被引用的数据。 对应代码：pipeline.hpp 把线程池成员放在所依赖数据之后声明，使其先析构并完成 join。
- **Drain 与 Cancel：**Drain 兑现所有已接收任务；Cancel 只移除仍排队的任务。已运行任务继续完成，二者都拒绝新提交。 对应代码：DeliveryCenter::shutdown(CloseMode) 复用线程池协议，取消的排队 future 返回 broken_promise。
- **计算与提交边界：**CPU 评分完成不等于业务发货完成；只有库存 checkout 形成明确业务结果才算完成提交。 对应代码：DeliveryResult 同时保留 order_id、Score 和 Receipt，避免把“算过路线”直接计为成功订单。
- **结果对账：**关店后按每个已接收任务的 future 统计值、业务拒绝、异常与取消，不能仅看“线程退出”日志。 对应代码：逐笔比较 score 与 oracle，核对 Accepted、duplicate、Conflict、Insufficient 与最终库存。
- **性能与正确性分离：**线程池吞吐量和密集计算速度要测量，正确性和安全关店则由确定的结果合同验证。 对应代码：make benchmark 输出真实串行、布局优化和并行耗时及校验；不规定必须达到某个加速倍数。

**完整推演：五个提交跨过 Cancel 关店**

1. 入口已接收 A、B、C、D、E，调用者持有五个 future。
2. A、B 已被 worker 取出，C、D、E 仍在队列中。
3. 控制线程调用 Cancel：入口关闭，C、D、E 被移除，其 future 变为明确错误。
4. A、B 继续完成评分和库存提交，然后 worker 退出并被 join。
5. 调用者读取五个结局：两个已执行结果加三个取消；新提交被拒绝。
6. 最后检查库存只包含真正完成的 Accepted 订单扣减，不根据排队数量扣减。

任务被接收、开始执行、完成计算、提交库存和线程结束是不同事实。

- 同号同内容不重复扣减，同号改内容返回冲突
- 并发成功数与最终库存相符，库存不为负

### 阶段 3：反向转仓与协作取消

- 转仓线程在有限测试内全部结束
- 双仓总量守恒，失败不留下半次转移
- 能够区分 stop 请求、观察取消与真正任务结束

- Drain 兑现已接收任务，Cancel 明确区分排队取消与运行完成
- 关闭后的新任务被拒绝，每个已接收 future 都有可解释结局
- 工作线程先回收，再释放引用数据；最终源码在干净目录可构建运行

## 如何判断作品完成

1. 按 manifest 的 30 个 copyFiles 增量从空工程累积，所有阶段能独立构建和运行，最终受管源码与 project 目录一致。
2. 新模块第一步的编译、第二步的真实调用和第三步的专项测试分别有证据，不能用之前测试通过替代当前模块验证。
3. 计算测试覆盖最小合法维度、平局、非法维度、样本数量不匹配、不同种子和布局等价；批次 API 另覆盖空批次、线程数超过订单数和异常。
4. 队列和池测试覆盖空/满等待、关闭唤醒、提交与关闭交错、排空、取消、任务异常、嵌套调用拒绝和重复关闭。
5. 库存测试覆盖唯一订单竞争、相同重试、内容冲突和失败重试；双仓模块测试反向转移、守恒、同仓输入和边界失败。
6. 停机验证逐个读取已接收 future 的结局，并核对真正提交的库存。只看队列为空或打印“已关店”不足以证明完成。
7. 基准记录真实机器、编译配置和实际耗时，不把提速当正确性证明。

这些测试是有代表性的证据，不是对所有调度交错的形式证明。RAII 异常路径测试验证公开行为与语言生命期合同，没有独立泄漏探测器时不能声称做过泄漏检测。协作取消测试覆盖协议和预取消行为，不承诺测出某个固定毫秒的实时响应上界。
