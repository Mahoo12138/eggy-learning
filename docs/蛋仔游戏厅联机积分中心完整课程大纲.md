# 蛋仔游戏厅联机积分中心完整课程大纲

## 课程定位与最终作品

超级凤凰蛋沿用“蛋仔游戏厅联机积分中心”的原方向：足球场和钢琴地毯的 C 终端上报比赛事件，C 网关接收并转发，C++ 服务使用 SQLite 保存积分、兑换和查询结果。它接续上一段位的封装、资源管理与并发基础，重点转向**真实网络边界与持久数据的一致性**。

最终不是三个同进程函数的演示，而是三个独立可执行进程，经两段本地 TCP 连接形成通路：

```text
C17 client
    │ 请求帧 / 响应帧
    ▼
C17 gateway（4 worker + 有界接入队列）
    │ 独立后端 TCP 连接
    ▼
C++20 service（4 worker + Store 单连接业务互斥）
    │ 参数绑定 / 显式事务
    ▼
SQLite：players + ledger + requests
```

课程逐步完成消息分帧、部分读写、绝对 I/O 期限、有限重试、有界网络并发、SQL 约束、C++ RAII、事务、持久幂等、稳定查询与同库重开。不会要求学习者看到“实现可靠协议”或“加入数据库事务”一句话后自行补出完整基础设施。

- 10 章，每章 1 节概念理解、3 节完整代码增量、1 节小范围独立变式，共 50 节。

## 协议与错误合同

完整帧由 **4 字节网络序无符号长度**，后跟 **1..4096 字节正文**组成。长度头本身也可能分片；正文不能含 NUL。最终网关与服务每条连接最多处理 16 帧。ID 和 player 只允许 1..32 位 ASCII 字母、数字、下划线、连字符；金额 1..1000000，余额范围 0..1000000。

| 请求 | 含义 |
|---|---|
| `PING|player` | 连通性与协议验证 |
| `ADD|event_id|player|amount` | 新增积分；必要时创建玩家 |
| `REDEEM|event_id|player|amount` | 消耗积分；没有额外奖品库存模型 |
| `BALANCE|player` | 查询当前余额；不存在的玩家返回 0，不创建玩家 |
| `TOP|limit` | 查询榜单，limit 为 1..10 |
| `HISTORY|player` | 按 seq 升序返回最早 20 条账本；没有分页 |

成功以 `OK|...` 返回，应用错误以 `ERR|CODE` 返回。传输失败最终由客户端汇总为 `ERR|TRANSPORT`；学习时可根据失败阶段分析 EOF、截断、等待耗尽与系统错误，但代码没有向终端返回一套精细网络错误枚举。非法命令/标识是 `BAD_REQUEST`；业务层可能返回 `INSUFFICIENT`、`LIMIT`、`CONFLICT`；数据库层可能返回 `BUSY`、`DB`。

数据库绑定能力比网络标识语言更宽。`tests/sqlite_unit.cpp` 直接使用 Statement 对由中文、单引号、内嵌 NUL 与末尾 bytes 组成的文本做原样字节往返；网络仍拒绝这些 player 字符。这两个边界不能混为一谈。

## 时间、并发与数据库写入边界

第 3 章起，客户端**每次尝试**有 1000ms 绝对 I/O deadline，连接、写帧、读帧共同消耗它。少量新字节、EINTR 或 EAGAIN 不重置它。RETRIES 为 0..2，即最多 3 次尝试；新尝试可建立新预算，所以整轮不是总共 1 秒。明确收到应用错误响应时，客户端直接返回，不自动重试 BUSY 或业务拒绝。第 8 章之前不允许写请求自动重试。

服务端和网关从接受连接时计算每连接 1000ms，包含接入队列等待与该连接最多 16 帧。网关后端转发沿用当前连接剩余预算；C++ 服务有它自己从 accept 开始的期限。这不是整个业务链路的一条统一事务 deadline。数据库业务可能已经开始，即使客户端等待结束，也不会强制中止事务。

网关与服务使用 4 个固定 worker 和容量 8 的接受队列。队列满时关闭新接入；停止时不再接收新连接，关闭排队会话，并等待在途处理结束。一个慢连接只占一个 worker；全部 worker 被占用时，正常请求仍可能等待或失败，课程只承诺实际定义的数量与期限边界。

Store 的一个 SQLite 连接由 mutex 覆盖完整业务操作。网络能并发接入，不代表同一连接上的写事务并行执行。SQLite 同时只允许一个写事务；本工程的 busy timeout 为 300ms，可能到期返回 `ERR|BUSY`。它不是成功保证，也不是所有 SQL 执行的硬期限。

## 持久事实、恢复与升级的区别

最终数据模型：

- `players(player, coins)`：玩家标识与当前余额。
- `ledger(seq, event_id, player, kind, amount, delta)`：ADD/REDEEM 的持久变化依据。
- `requests(event_id, fingerprint, response)`：第 8 章引入的请求指纹与既定响应。

请求指纹使用操作类型、玩家和规范化金额，`0005` 与 `5` 是相同业务值。相同 ID 同指纹返回首次保存的响应，不再次改余额；相同 ID 改玩家、金额或操作返回冲突。首次响应中的余额是历史快照，当前余额应使用 BALANCE 查询。

积分不足或余额超限等确定业务拒绝也持久保存，即使之后余额变化，旧 ID 仍返回原拒绝；新的业务尝试需要新的 ID。DB/BUSY 等未提交故障不会被保存成既定业务结果。requests 不自动淘汰，长期服务需要另行设计容量与保留规则。

课程通过显式故障开关观察关键窗口：

- `ARCADE_TEST_FAIL_AFTER_DEBIT=event_id`：余额已更新、账本尚未写入时抛错，检查整笔事务回滚。
- `ARCADE_TEST_DROP_ACK_ONCE=event_id`：一次新请求已 COMMIT 成功后关闭连接而不发送响应，检查同身份重试恢复原结果。重放旧结果不再次触发这次故障。

逐节测试使用隔离数据库。最终持久数据库从最终 schema 创建，再测试关闭和重开；没有提供把第 6、7 章可能含重复账本的旧数据库自动升级到第 8 章约束的迁移工具。`CREATE TABLE IF NOT EXISTS` 不等于通用迁移。

数据库配置使用 WAL 和明确同步设置，但 WAL 不是备份策略。当前恢复验证针对实际进程停止/重新启动与提交窗口，不等于模拟过断电、磁盘损坏或存储设备错误。持久幂等保证同一数据库中已提交身份的业务效果去重，不宣称 TCP 只投递一次，也不提供未实现的外部系统事务。

## 第 1 章：先让 C 终端与网关建立真实连接

**目标：**理解网络端点和监听/连接描述符，从本地请求模型推进到 C 终端与网关的真实 TCP 往返，为后续 C++ 服务预留边界。

**阶段：**网络边界。**章末状态：**`network-model-3`。

### 概念小节：连接成功和业务处理完成为什么不是一回事

第一个代码步骤只在本地验证 PING|player 并输出响应；它不是网络。第二步才让 C 客户端连接 C 网关。本章网关自己回应 PING，C++积分服务直到第六章才加入。connect成功仍只说明传输连接建立，不代表最终数据库业务已经完成。

IP和端口定位端点。监听socket负责accept，每次成功接受会话获得新的连接fd。本章终端发送最多4096字节请求，再shutdown(SHUT_WR)关闭发送方向，网关读到EOF才知道本次请求结束并回复；一条连接只做一次请求。这个可运行起点保留读取方向，但无法复用会话，下一章才用长度帧解决。最终网关还会连接独立C++服务，本章尚未接入。

- **IP 与端口：**IP 指向网络接口或主机地址，端口区分同一地址上的服务；本课程使用本地回环减少网络部署变量。 对应代码：network-model-1阅读common/protocol.h中的PING|player；step2阅读网关一个监听端口与客户端connect参数。
- **监听 socket 与连接 socket：**监听描述符用来 accept；每次成功 accept 获得独立连接描述符，真正收发数据在后者进行。 对应代码：对照网络辅助函数与服务入口中 socket、bind、listen、accept、connect 的返回值。
- **进程与连接生命周期：**本章只有C终端与C网关两个进程。每个进程管理自己的fd，连接关闭不等于监听结束；第六章才增加第三个C++服务。 对应代码：网络步骤中raw_read读到EOF结束正文；客户端shutdown(SHUT_WR)只关发送方向，之后继续收响应。
- **传输确认与业务结果：**连接成功或 send 成功只描述传输层操作，业务结果必须由应用解析并返回。 对应代码：暂时观察网络响应；数据库提交结果会在后续事务与端到端步骤接入。

**执行推演：从本地 PING 到一次真实 TCP 往返**

1. 运行第一步client PING|alice，只验证本地输入与回显，不把它当网络证据。
2. 第二步启动gateway监听一个端口，client连接该端口并发送PING正文。
3. 客户端shutdown(SHUT_WR)，网关读到EOF后把完整正文交给ping_reply。
4. 客户端读取OK|PONG|alice后关闭连接；网关的监听socket仍保留。
5. 再次连接发送另一位合法玩家的PING；确认这是新会话，并认识到本章每次请求必须结束发送方向。

用EOF作边界足以建立受限起点，但不能在同一连接继续发送第二个请求；下一章用长度前缀改进。

**理解检查：**

- 服务端应从哪个描述符读取一位客户端的请求？
- 本章客户端调用shutdown(fd,SHUT_WR)后，为什么还能接收网关响应？
- connect 返回成功后客户端立即崩溃，可以断定什么？

## 第 2 章：把字节流还原成一条条事件

**目标：**用有上限的长度帧处理分片、粘连、部分读写和半帧断开，使协议边界独立于 TCP 分包。

**阶段：**网络边界。**章末状态：**`message-framing-3`。

### 概念小节：一次 send 为什么不等于一次 recv

终端先发送事件 A、再发送事件 B，接收端可能一次拿到 A 的前半段，也可能一次拿到 A 和 B。TCP 只保证连接内按序字节流，不保证保留应用调用时的消息边界。

应用协议自己给消息加边界：先读取固定宽度长度头，转换约定字节序，检查长度合法，再读取恰好那么多载荷。每次 read/write 只推进实际完成的字节数，剩余部分继续处理。帧大小先验证再分配/写入缓冲，EOF 落在帧中间是截断，不能拿半条请求交给数据库。

- **TCP 字节流：**传输的是有顺序的字节序列，应用消息需要由协议自己分隔；网络拆分和合并与业务条数无关。 对应代码：对照协议函数与分片/粘连测试，不以 recv 调用次数计算消息数。
- **长度前缀与字节序：**固定宽度头表示后续载荷长度，多字节整数按统一顺序编码，避免发送与接收的本机表示不同。 对应代码：common/frame.h 使用4字节uint32_t长度头、htonl/ntohl网络字节序；正文长度1..4096，不能嵌入NUL。
- **部分读写与偏移：**系统调用返回实际完成数量，可能比请求数量小；下一次应从未完成位置继续。 对应代码：common/net.h 的 io_exact 维护done与length-done，frame_read/frame_write分别调用它完成头与体。
- **长度上限与截断：**先限制载荷长度再接收，避免无限内存占用；只读到部分头或部分体后 EOF 是协议不完整。 对应代码：frame_read先拒绝0、4097或0xffffffff等非法长度，正文含NUL也拒绝；不完整帧关闭会话，不交给业务。

**执行推演：长度为 5 的载荷分三次到达**

1. 协议长度头先到一部分，接收状态仍在“读头”，不能解释尚未完整的长度。
2. 长度头完整后解码为 5，并与最大长度比较。
3. 载荷先收到 2 字节，偏移变 2，仍需 3 字节。
4. 再收到 1 字节，偏移变 3；最后收到 2 字节，才把 5 字节完整载荷交给应用。
5. 若第 3 字节之后 EOF，应报告截断，不能把已有 3 字节当成合法事件。

状态依据协议字节数推进，与网卡分包或 send/recv 次数无关。

## 第 3 章：给掉线、等待和重试划定边界

**目标：**用单调时钟和有限重试区分 EOF、失败、超时与提交结果未知，防止慢连接无限占用。

**阶段：**网络故障处理。**章末状态：**`disconnect-timeout-3`。

### 概念小节：超时没有收到回答，积分到底加没加

终端把完整事件发送出去后等待响应；服务已经处理，但连接在响应途中断开。终端只看到超时，不能据此判断数据库没有提交。另一种慢连接每隔一会儿送一个字节，如果每次重置超时，就永远占着资源。

每次客户端尝试建立一个now_ms()+1000的I/O deadline，connect、发送和接收共用剩余预算；服务端从accept起也使用一条连接的固定期限。poll与非阻塞send/recv处理EINTR/EAGAIN时不刷新deadline。客户端重试参数0..2，最多3次尝试，每次可获得新的1秒预算；最终传输失败统一输出ERR|TRANSPORT。它不是整轮重试仅1秒，更不是SQLite事务或等待Store互斥量的硬期限。第八章前禁止自动重试写请求。

- **EOF 与系统错误：**recv 返回 0 表示对端关闭发送方向；负值要结合 errno，EINTR、EAGAIN 和真正故障含义不同。 对应代码：io_exact把EOF、等待耗尽和不可恢复I/O错误汇总为失败；学习时读对应分支，客户端最终只报告ERR|TRANSPORT，不伪造更细分类。
- **单调时钟与总期限：**单调时间用于测持续时长，不受系统日历时间校正影响；总期限跨越一次逻辑操作的多个等待。 对应代码：now_ms采用CLOCK_MONOTONIC；一次连接/尝试内共用deadline，客户端新的有限尝试会新建预算，不能把二者混为一个全局1秒。
- **有限重试：**重试需要明确原因、次数或总预算；坏输入和业务拒绝不能通过重复提交修复。 对应代码：client PORT REQUEST [RETRIES 0..2]；明确收到ERR应用响应时直接返回，不自动重试；第八章持久幂等启用后才允许写请求重试。
- **结果未知：**没有收到结果不等于没有执行；响应与提交之间存在无法从客户端直接观察的窗口。 对应代码：记录并重用请求 ID；后续持久幂等章节把重试映射到已保存结果。

**执行推演：一次连接内的1000毫秒与两次尝试的区别**

1. 一次客户端尝试从T设deadline=T+1000ms，连接、写帧和读响应共用它。
2. 连接和写帧花300ms，读响应最多只剩约700ms；少量进度不重置它。
3. 完整响应在期限内仍未到，当前连接失败并关闭。
4. 若RETRIES=1，可进行第二次尝试并新建一次预算，总共最多2次，而不是整轮只有1秒。
5. 最终仍失败输出ERR|TRANSPORT；若写请求已发出，结果可能未知，直到第八章有持久幂等后才允许安全自动重试写动作。

总期限控制资源占用，幂等身份控制不确定结果下的业务重复，两者不能互相代替。

**理解检查：**

- 每收到一个字节就重新给 1 秒，会产生什么问题？
- 完整请求发出后超时，客户端能断言什么？
- 对结果未知的同一业务动作重试，ID 应如何处理？

## 第 4 章：让多个终端共享有限的接待能力

**目标：**用固定工作线程与有界接入队列隔离连接状态，明确慢连接、队列满和关闭时的资源边界。

**阶段：**网络故障处理。**章末状态：**`multi-client-3`。

### 概念小节：一个终端停在半帧，为什么别的终端还应该有机会完成

足球场连接后只发出半个帧头，钢琴地毯随后发送完整请求。串行服务若一直等前者，后者无法获得处理机会。无限创建线程虽然绕过一次阻塞，却把风险转成无限资源占用。

接收线程只负责 accept 与有界入队，固定 4 个 worker 分别独占当前连接并处理其前后端 I/O。等待队列上限为 8，队列满时明确关闭新的接入。连接的绝对 deadline 从接入阶段记录，排队不额外获得无限时间。一个慢连接最多占一个 worker；全部 worker 都慢时仍会等待，但总资源和等待期限有界。

- **连接状态隔离：**每个会话各自拥有描述符、读写进度和帧缓冲，不能把 A 的半帧与 B 的数据拼在一起。 对应代码：common/server.h 分发连接，处理函数使用会话本地缓冲和 deadline。
- **固定工作线程：**最多固定数量线程同时执行连接处理，不随客户端数量无限增长。 对应代码：课程服务器使用 4 个 worker；一个阻塞会话只占其中一个名额。
- **有界接入与背压：**队列容量限制等待处理的连接，超出负载时明确拒绝，避免用无限内存和描述符承接一切。 对应代码：接受队列容量为 8，满队列路径关闭新连接；客户端将看到传输失败。
- **排队时间与总预算：**任务在队列里等待同样消耗用户等待时间，不应 dequeue 后才重新获得整份预算。 对应代码：从接受连接时记录的 deadline 传给 worker，取出后先检查还剩多少时间。

**执行推演：4 个 worker 和 8 个排队位置怎样处理慢终端**

1. 客户端 A 进入 worker 1，只发送半条请求，等待受原 deadline 限制。
2. B、C、D 由其余 worker 处理，A 不必先结束它们才能执行。
3. 若又来更多连接，最多 8 个在接受队列等待。
4. 所有 worker 都被慢连接占用且队列已满时，新的连接被关闭，不能承诺所有请求立即成功。
5. A 到期释放会话，worker 1 取下一连接；其排队时间已经计入 deadline，可能直接发现期限已过。

隔离一个慢连接与无限承诺服务能力不同；有界系统必须定义过载结果。

- 连接在队列等了 700ms，原总预算 1000ms，开始处理时应剩多少？

### 概念小节：变量记住了积分，为什么重启后就没了

players(player,coins)保存每位玩家的当前余额，ledger(seq,event_id,player,kind,amount,delta)保存变化来源。player主键、ledger外键和CHECK约束保护已定义形状；外键必须在每条连接上开启。本章不会把尚未加入的event_id唯一性或多语句事务冒充已完成能力：它们分别在第八章和第七章补齐。

- **表、行与主键：**表组织同一种事实，行是一条记录，主键稳定地区分记录；主键不能靠查询返回顺序猜测。 对应代码：db/schema.sql当前只有players和ledger；players.player唯一，ledger.seq是自增主键，ledger_player_seq索引用于按玩家查历史。
- **唯一约束与业务标识：**唯一约束阻止同键多行。本章用players.player学习主键唯一，ledger.event_id暂不唯一；第八章再加入事件唯一索引与持久结果表。 对应代码：重复players.player由主键拒绝；不能在第五章声称重复event_id已经被去重。

### 概念小节：玩家名字带一个单引号，为什么不应该破坏 SQL

网络协议的玩家/事件标识只接受ASCII字母数字、下划线和连字符，不能发送引号、中文、分隔符或NUL。独立本地tests/sqlite_unit.cpp则把由中文、单引号、内嵌NUL与末尾bytes组成的文本通过Statement绑定并原样查回，验证SQL结构与数据的边界。异常路径还要释放已获得的语句和连接。

SQL 模板先由 prepare 解析，参数位置固定；玩家名、事件 ID 和数值通过 bind 作为值进入。step 返回 ROW、DONE 或错误，调用者按合同分支。Statement 拥有 sqlite3_stmt，Connection/Store 拥有连接，析构完成 finalize/close。这里使用一条数据库连接并通过 mutex 串行保护业务调用；网络多个 worker 不直接同时操作它。

- **SQLite C API 与结果码：**SQLite API 用显式返回码报告打开、准备、执行的结果；ROW、DONE 和错误不能混为成功。 对应代码：service/sqlite_raii.hpp定义Database与Statement；service/store.hpp定义Store::handle。检查sqlite3_open_v2/prepare_v2/bind/step返回码与SqliteError。
- **预编译语句与参数绑定：**语句结构先确定，用户输入作为参数值传入，所以引号不会变成 SQL 语法。 对应代码：Statement::text使用value.data()与显式size绑定；网络Store仍只接受ASCII标识，本地sqlite_unit.cpp验证中文、单引号、NUL与bytes作为数据原样往返。
- **RAII 与借用结果：**连接和语句句柄分别有唯一回收责任；SQLite 返回的列文本可能只在语句当前状态下有效，持久使用时需要复制。 对应代码：Statement析构finalize；text读取使用sqlite3_column_bytes复制完整结果，包含内嵌NUL；Database在构造中配置失败时主动close，因为失败对象不会执行其自身析构。
- **单连接访问边界：**本工程一条连接由 mutex 保护，避免网络 worker 把同一连接上的多语句事务交错。 对应代码：Store::handle持std::mutex覆盖完整业务调用；Database以FULLMUTEX打开并设置foreign_keys与300ms busy_timeout，事务章节才增加业务多语句原子性。

## 第 7 章：让记账与余额修改一起完成

**目标：**把加分和兑换的多语句更新收束为显式事务，用提交、回滚和故障注入证明没有半完成业务状态。

**阶段：**事务与恢复。**章末状态：**`transactions-3`。

### 概念小节：记录写成功了，余额更新失败，算不算完成

兑换先扣余额、后记记录，第二条语句失败就可能出现少了积分却没有兑换依据。反过来先记兑换、后扣余额，也可能留下没付分的成功记录。把异常 catch 后继续打印成功不能解决这种问题。

一次业务动作从 BEGIN 到 COMMIT 包住所有需要一起成立的写入。只有每一步都成功才提交；任一步失败就回滚。Transaction 对象让未提交退出走回滚路径，网络等待不应被随意放进长事务。SQLite 允许多读者，但同一时刻只有一个写事务；BEGIN IMMEDIATE 也可能因为外部写者而 BUSY，等待超时不是保证成功。

- **事务与原子性：**事务让一组写入要么作为整体提交，要么全部不生效；不是几条顺序执行 SQL 的别名。 对应代码：Transaction在service/sqlite_raii.hpp；Store一次业务同时更新players.coins和插入ledger，REDEEM表示消耗积分，不管理额外奖品库存表。
- **BEGIN、COMMIT 与 ROLLBACK：**BEGIN 开始事务，COMMIT 确认全部变更，ROLLBACK 撤销未提交变化；每个调用仍可能失败。 对应代码：检查 transaction 的 committed 标记和所有异常出口，未成功提交时走回滚。
- **SQLite 写竞争与 BUSY：**不同连接可竞争同一数据库写锁，SQLite 同时只允许一个写事务；有限 busy timeout 只限制等待。 对应代码：Database设置sqlite3_busy_timeout(...,300)；外部连接BEGIN IMMEDIATE持锁时，服务可能返回ERR|BUSY，此应用响应客户端不自动重试。
- **故障注入与状态对比：**在真实写入之间故意触发错误，用前后查询证明原子性，而非仅检查错误文字。 对应代码：ARCADE_TEST_FAIL_AFTER_DEBIT匹配事件ID时，在余额更新后、ledger插入前抛错；测试比较coins、ledger行数与SUM(delta)。

## 第 8 章：响应丢失后仍只记一笔业务

**目标：**持久保存请求 ID、内容与结果，使断线重试和服务重启后的重复请求保持同一业务效果。

**阶段：**事务与恢复。**章末状态：**`durable-idempotency-3`。

### 概念小节：已经提交但回答没送到，怎样既能重试又不重复加分

服务已完成加分并 COMMIT，但发送响应前故意断开连接。客户端无法知道结果，所以重试。若去重只存内存，服务重启后会忘记旧 ID；若只查余额，也无法知道是哪一条事件改变了它。

第八章新增requests(event_id,fingerprint,response)及ledger.event_id唯一索引。指纹按操作类型、玩家和规范化整数金额构造，0005与5是相同业务内容。事务内查ID：同指纹返回原response，不再修改；不同指纹返回ERR|CONFLICT。新ID的业务效果与结果同事务提交，包含积分不足/上限等既定拒绝结果。旧响应里的余额是当时快照，当前值要BALANCE查询。本章演示使用隔离新库，未提供把前章重复账本自动迁移的工具。

- **幂等键与请求指纹：**ID 表示一次业务动作，指纹保存操作类型、玩家和金额等含义；同 ID 但内容不同应冲突。 对应代码：Store::mutate规范化指纹为op|player|to_string(amount)；同ID改类型/玩家/金额冲突，0005与5不产生伪冲突。
- **持久结果与重放：**数据库记录已确定响应，使重试获得同一事实，而非根据当前余额随意重算原结果。 对应代码：requests持久保存成功和INSUFFICIENT/LIMIT结果；即使后续余额增加，原拒绝仍重放。ERR|BUSY/DB等未提交故障不被当成既定业务结果缓存。
- **提交后丢响应：**事务提交和客户端收到回答是两个独立时刻，中间断线让客户端处于结果未知。 对应代码：ARCADE_TEST_DROP_ACK_ONCE指定ID；首次新业务提交后service关闭该连接不写响应，真实client用相同正文有限重试。
- **业务去重的保证范围：**本例保证同一数据库中的相同请求不会重复造成业务变更，不保证网络只传一次，也不覆盖未实现的外部系统。 对应代码：幂等记录与余额处于同一SQLite事务；服务重启重新读库而非清空去重表。

**执行推演：请求 E 加 10 分，提交后响应丢失**

1. 玩家 P 原余额 20，终端发送 ADD|E|P|10。
2. 服务在事务内记录 E 的内容，把余额改为 30，保存成功响应并 COMMIT。
3. 响应发送前连接断开，终端不知道这笔是否完成，但保留 E 与原正文。
4. 终端有限重试同一请求，服务查到 E 和相同指纹，返回保存的原响应，余额仍为 30。
5. 服务重启后再提交 E，记录仍在；改成 ADD|E|P|11 则返回冲突，不能再加 11。
6. 若旧请求结果是INSUFFICIENT，之后余额增加仍返回这次已定拒绝；想发起新的业务尝试应使用新ID。

持久身份和业务修改必须同事务提交，否则重试仍可能遇到“有去重键却没业务”或反过来。

## 第 9 章：让重启后的积分和榜单仍可信

### 概念小节：两位玩家同分，排行榜为什么不能随重启换顺序

数据库没有承诺按插入顺序返回普通 SELECT。两位玩家积分相同时，只有分数排序仍不能决定先后。服务重启后若从内存零值重新建立余额，还会把已提交数据覆盖掉。

打开使用最终schema创建的同一数据库，保留已提交数据，重新建立foreign_keys和busy等连接配置。TOP用coins DESC、player ASC排序，limit范围1..10；HISTORY按seq ASC最多20条。完整账本对账通过测试里的SQL SUM(delta)，不把20条历史窗口当全部历史。此课验证进程停止/重开，不包含章节旧schema迁移、物理掉电或磁盘损坏保证。

- **持久恢复与进程内存：**重启会丢失进程变量，已提交数据库记录是恢复依据；不能用内存默认值覆盖它。 对应代码：服务启动打开已有路径并保留表中记录，查询不要求先重播所有客户端请求。
- **ORDER BY 与稳定平局：**排序必须明确全部需要的决胜规则；本例榜单先分数降序、同分再按玩家标识升序。 对应代码：TOP 查询使用 ORDER BY coins DESC, player ASC，limit 受协议上限约束。
- **只读查询与审计历史：**查询展示事实，不暗中修正余额；历史解释余额变化来源，关联请求身份帮助排查。 对应代码：BALANCE无玩家返回0且不创建玩家；TOP限制1..10；HISTORY按seq ASC最多返回20条，是有界历史窗口，不是所有历史或分页接口。
- **恢复验证的边界：**进程崩溃/重开测试验证已提交记录与回滚行为，不等于电源故障、硬件写缓存或损坏磁盘测试。 对应代码：测试终止并重新启动服务，复用同一数据库，核对提交前后状态而不宣称永不丢数据。

3. 网络测试覆盖字节切片、相邻帧、长度上限、NUL、半帧断开、停发超时、有限重试及慢连接并发，不仅检查端口能连接。
4. SQL/C++ 测试覆盖约束、绑定字节保留、错误传播、打开失败和本地资源生命期；没有独立检测的资源行为不冒称检测通过。
5. 事务验证在真实写入之间失败，查询余额与账本证明没有半完成；写锁竞争能够得到明确 BUSY，释放后恢复。
6. 幂等测试同时覆盖相同指纹、规范化金额、变更玩家或金额冲突、并发同 ID、确定拒绝重放、提交丢响应与同库重开。
7. 查询测试覆盖空榜单、同分二级排序、limit 边界、历史窗口和重新打开；完整账本对账使用 SQL，不把 HISTORY 的前 20 条当全部历史。
8. 全链路测试真实启动三进程；最终另有两个服务实例共享一个 SQLite 文件的写竞争验证，证明不只依赖单进程 mutex。
9. 每个已发出请求的结局与数据库事实一致。没有响应只说明未知，不能凭日志或默认值把它说成成功或未执行。
